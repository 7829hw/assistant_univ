## 1. 공정한 비교를 위한 채점

### n31·m31이 v3에서 오답인 이유

채점기 v3는 실행된 모든 `get_place_scope` 호출을 정답 조회 집합·횟수와 비교한다(`place_lookups_ok`, `place_lookup_count_ok`).
실패한 조회도 그대로 들어간다.

| 문항 | 실행 경로 | v3 판정 |
|---|---|---|
| n31 "대구 두산동 도로 … RPM 평균" | 조회 `두산동 도로`(NOT_FOUND) → 장소 값 재질의 → 조회 `두산동/대구` → 분석 호출 인자·답변 정답과 같음 | 조회 집합에 실패한 `두산동 도로`가 있어 집합·횟수 불일치 → 오답 |
| m31 "부산진구 소속 택시 … 가장 적은 요금" | 조회 `진구/부산`(NOT_FOUND) → 재질의 → 조회 `부산진구` → 분석 호출 인자·답변 같음 | 같은 이유로 오답 |
| m10 "부산진구에서 대구 중구로 …" | `부산진구/부산` 성공, `대구 중구/대구` 실패 → 재질의 → 두 장소 다시 조회(중복) → 분석 호출 | 조회 키(지역 표기) 불일치와 중복으로 오답 |

실패한 조회는 scope를 돌려주지 않으므로 분석에 쓰일 수 없다. 세 문항 모두 최종 분석 호출의 scope는 정답 장소와 같은 scope다.

### 축을 나눈 채점(v4-axes)

v3 범주는 보존하고, 같은 저장 관측에서 세 축을 따로 계산한다(`evaluate_vendor100.py axes`, 모델 호출 없음).

1. **의미**: 최종 분석 호출의 Tool·인자·답변 값.
   - 정답 장소는 이 run의 조회 결과가 아니라 **정답 조회를 같은 실행기로 푼 scope**와 비교한다. 이름·지역 표기가 달라도 제공자가
     같은 scope로 풀면 같은 장소다. 잘못된 장소의 scope가 최종 호출에 들어가면 답변 숫자가 우연히 같아도 오답이다.
   - mock scope 값에는 주변 포함이 드러나지 않으므로, 그 scope를 만든 조회의 `include_vicinity`가 정답과 같아야 한다.
   - 정답이 조회 결과를 요구하는 인자의 scope는 이 run에서 성공한 조회의 결과여야 한다(출처). 분석 호출은 하나.
2. **경로**: 장소 조회를 쓰임(최종 호출이 쓴 scope)·실패(오류 반환)·중복(앞과 같은 조회)·폐기(성공했지만 최종 호출이 안 씀)로 나눈다.
   분석 호출 오류, 정답보다 많은 조회도 센다. "정상 답변이면서 경로가 깨끗함"을 따로 센다.
3. **비용**: 계획·재질의 호출, 재질의 실패, 정상 답변 중 재질의를 거친 수, 문항 지연(합계·중앙값·p90·최대), 생성 토큰, thinking 길이.

행동 테스트 `tests/test_scoring_axes.py`(9건): 실패 조회 폐기 → 의미 정답·경로 불결; 잘못된 장소를 분석에 쓰면 숫자가 같아도 오답;
잘못된 장소를 조회했지만 버림 → 의미 정답·경로 "discarded"; 지역 표기만 다른 같은 장소 → 정답; 주변 포함 차이 → 오답;
조회로 만들지 않은 scope → 오답; 조건이 다르면 숫자가 같아도 오답; 질문에 적힌 scope literal → 조회 불필요; 출발·도착 뒤바뀜 → 오답.

**기존 기록에 적용:** 모든 비교 대상에 같은 함수를 적용했다.

| 기록 | v3 정상 | 축별 정상 | 바뀐 문항 |
|---|---|---|---|
| grounding_v7 최종(qwen3:8b, 311) | 222 | 225 | n31·m31(실패 조회 폐기), m10(실패·중복 조회, 지역 표기) |
| v8 P2 | 208 | 211 | dev/003·m31(지역 표기만 다름), m10 |
| v8 P5 | 217 | 218 | m31(지역 표기) |

잘못된 장소·조건이 통과된 문항은 없다. 바뀐 문항은 모두 경로 축에 실패·중복 조회 또는 정답과 다른 조회 표기가 남는다.

### OD 층별 지표

trip 건수 문항마다 최초 원출력 → 형식 정규화 → 조건 보존 → 재질의 뒤 grounding → 실행 호출에서 **장소 끝**(장소 scope × pickup/dropoff,
od_role both는 두 끝)과 **묶는 끝**(dimension이 있을 때, 생략 = both)을 각각, 그리고 **둘 다** 맞았는지 센다.

- **모델 교체: 채택하지 않음.** 다만 가설 H-model은 강하게 지지된다. 같은 코드·prompt·평가에서 qwen3.8:27b는 최초 grounding
  의미 정확 134 → 250/320, 조용한 오답 26 → 6, held-out 정상 30 → 40을 보였다. 비용은 중앙값 지연 1.6배, VRAM 10.7 → 17.3GiB이고,
  재질의·timeout·꼬리 지연은 줄었다. 막은 것은 모델 용량이 아니라 계약 설명의 빈틈 하나(trip과 taxi_status)다.
- **설명 정정 D: qwen3.8:27b에서만 기준 충족, 현재 모델에는 채택하지 않음.** qwen3:8b에서는 같은 설명이 trip 밖으로 번져 회귀했다
  (v8 P2·P5와 같은 양상). D는 `grounding-v9-desc` 브랜치(`70ca434`)에 보존한다.

## 8. 다음에 검증할 가설 하나

> **trip Tool은 운행 상태 조건을 받지 않는다는 계약 사실을 설명에 알리면, qwen3.8:27b의 `taxi_status` 정지가 사라지고
> qwen3.8:27b + D가 모델 교체 기준 2(OD 대조)를 포함한 사전 등록 기준을 모두 충족한다.**

- 근거: 전체 run에서 정지 24–25건 중 20–21건은 그 조건만 빼면 정답 grounding과 같다. qwen3.8:27b + D가 잃은 19문항 중 18문항이 이 정지다.
- 현재 prompt는 "실차·공차·대기영업은 taxi_status 조건"이라고만 한다. 검증기는 trip 계산에서 이 조건을 받지 않는데, 모델은 그 사실을 듣지 못했다.
- 주의할 점: "공차 실차 구간"처럼 trip으로 계산할 수 없는 조건(n26)은 거부가 정답이다. 그래서 조건을 지우는 것이 아니라 계약을
  알리는 설명이어야 하고, 코드의 의미 보정으로 처리하지 않는다.
- 이번 held-out은 이 결과를 보고 다음 후보를 정하므로 다음 검증의 최종 평가로 쓰지 않는다.
