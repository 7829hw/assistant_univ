작성: 2026-10-05.
- grounding_v13 채택(b62f6dc) 뒤의 **별도 운영 조건 검증**이다. v13의 사전 등록 기준 충족과 채택 기록은 그대로 둔다.
- 이 문서는 진단(1절)과 v13 기록에 확장 지표를 적용한 결과(`runs/retro_report.json`)를 본 뒤, 운영 검증 실행 전에 고정한다.
- 새 prompt 후보와 모델 탐색은 하지 않는다. 질문별 예외, 정규식 의미 보정, 새 근거 필드, 추가 검증 모델 호출도 없다.

내리고 실행하면 6/6이 재현됐다.

요청 기록 프록시(`record_proxy.py`)로 실제 요청을 비교했다(B 조합, 같은 6문항, `compare_requests.py`).

- `prompt_eval_count`는 모든 경우 전체 prompt 길이와 같았다. 서버가 보고하는 값으로는 prompt 캐시를 재사용한 흔적이 없다.
- **관측:**
  - 애플리케이션은 같은 요청을 보낸다.
  - 같은 요청의 출력은 그 모델이 직전에 처리한 요청에 따라 달라진다.
  - 직전 처리 이력이 같으면 출력도 같았다.
  - 적재 직후의 첫 요청은 재현된다.
  - temperature 0은 같은 서버 상태에서의 반복만 보장했고, 서버 상태가 다르면 출력이 달라졌다.
- **가설(입증 안 됨):** Ollama/llama.cpp 서버 쪽의 상태가 직전 요청에 따라 남는다. 후보는 KV 캐시 슬롯 내용·배치 구성·커널
  선택이다. 이번 단계는 서버 내부를 조사하지 않는다. 원인 규명이 아니라, 그 결과(질문 순서에 따른 출력 차이)가 품질에 주는 영향을 잰다.
- **평가에 주는 뜻:**
  - 지금까지의 평가 조건(문항마다 해제)은 "적재 직후"라는 하나의 고정된 서버 상태다.
  - 연속 사용에서는 직전 질문에 따라 다른 출력이 나온다.
  - 적재 직후 상태가 더 "올바른" 상태인 것은 아니다.

## 2. 통제 장치 (이번 단계에서 추가, 테스트 `tests/test_operational_controls.py`)

- **평가 harness(`evaluate_vendor100.py llm`):**
  - `--reference-date`: 기본 2026-09-25. 기존 정답 셋의 기준일이다.
  - `--model-state`: 기본 `unload_per_question`(기존). `keep_loaded`면 시작할 때만 모델을 내린다.
  - `--order`: 기본 `file`. `reverse`, `shuffle:SEED`도 고를 수 있다.
  - 세 값은 행마다 `run_settings`로 남고 meta에는 `item_order`가 남는다. 이어 실행할 때 조건이 다르면 멈춘다.
  - 기본값은 기존 동작과 같고, 기록 재적용(`--replay-from`) 경로도 그대로다.
- **CLI:**
  - `--reference-date`: 기본은 실제 날짜(기존). 지정하면 조건 계층과 컴파일에 같은 날짜가 들어가고, planner prompt는 바뀌지 않는다(테스트).
  - 저장 기록에 `geoflow_settings`(기준일 포함)와 `geoflow_verification`이 남는다.

## 3. 고정 조합과 실행 범위

| 이름 | 모델 | prompt | 코드 |
|---|---|---|---|
| T2PC (채택) | qwen3.8:27b `aaee06c39dcf…` | 87048d0c | dev-v2. geoflow/·prompts/는 b62f6dc와 같음 |
| B (이전 기본, 조합 전체 복원) | qwen3:8b `500a1f067a9f…` | 522aa3b1 | b62f6dc revert(geoflow/·prompts/ = `grounding-v12-baseline`) |

- qwen3:8b + 현재 코드·prompt는 회귀가 확인된 조합이다(v13). 되돌리기 대상이 아니므로 돌리지 않는다.
- **문항:** grounding_v12 최종 56문항이다(v13에서 처음 사용, 이번이 두 번째). 운영 회귀 확인에만 쓰고 독립 held-out이라고 주장하지 않는다.
- **공통 설정:**
  - 기준일 2026-09-25, `--condition-check`, temperature 0, think 미지정, timeout 300초, mock·legacy.
  - 모든 요청은 기록 프록시를 거친다(누출·요청 동일성 확인용).

| 조건 | model-state | order | 조합마다 |
|---|---|---|---|
| C1 | unload_per_question | file | 1회 (v13 같은 조건 기록과 반복성 비교) |
| W1 | keep_loaded | file | 1회 |
| W2 | keep_loaded | reverse | 1회 |
| W3 | keep_loaded | shuffle:14 | 1회 |

**제한된 조건 확인(먼저):** T2PC로 6문항(`grounding_v13/cli_check_questions.yaml` 순서)을 두 경로로 실행한다.
- 경로 1: harness `keep_loaded`.
- 경로 2: CLI `--reference-date 2026-09-25` 연속 실행.
- 확인 내용: 요청 순서와 본문이 같은지, 출력이 같은지. 같으면 harness의 `keep_loaded`를 CLI 연속 실행의 채점 가능한 대리로 쓴다.
- 다르면 원인을 찾아 기록하고, harness 구현 오류이면 고친 뒤 다시 확인한다.

**모델 호출 예산:** 질문 실행 기준 최대 480회다. 재질의는 질문마다 최대 1회다.
- 본 실행: 4조건 × 56 × 2조합 = 448.
- 조건 확인: 12.
- 재실행 여유: 20.
- 이를 넘는 반복은 하지 않는다.

**중단 조건:**
- 한 run에서 실패한 LLM 호출(timeout)이 5%를 넘거나 harness 오류가 나면 멈추고 원인을 기록한다.
- C1의 모델 해제가 실패하면 그 run만 1회 다시 한다.

**한계:** 순서 3개(W1–W3)와 C1 1회로는 질문별 변동률이나 순서 효과를 충분히 추정할 수 없다. 이번 측정은 "운영 조건에서 품질
판단이 바뀌는가"를 보는 제한된 확인이다.

## 4. 지표 (`report.py`)

- **분류:** v4-axes 다섯 분류.
- **v13 사전 등록 U:** 그대로 쓴다(소급 변경 없음).
- **확장 요구 보존 R:** v14에서 정의한 다음 평가용 지표다.
  - R1 요구 조건 버림(= U1).
  - R2 표현할 수 없는 요구 버림(m40형).
  - R3 정해지지 않은 의미 채움(c08b·g44형).
  - R4 승하차 기준 대신 기본값(f03형).
- **멈춘 문항의 해석(S):** 멈춘 문항에서 최종 grounding의 측정값·date·time·taxi_type·taxi_status를 정답과 비교한다(v06형). 멈춘 사실과 바르게 해석한 사실을 나눠 센다.
- **거부 정확성:** v11 정의.
- **비용:** 지연 중앙값·p90, 모델 적재 시간 합, 재질의, timeout.
- **변동:** 같은 질문의 최초 grounding, 최종 grounding, Tool 인자, 분류가 바뀌었는지 본다. grounding은 문구 차이(개념 text·id)와 의미 차이로 나눈다.
- **표시 문항:** v13 라벨 점검의 표시 6문항은 포함한 값과 뺀 값을 함께 보인다.

U와 R의 범위 차이:
- U는 답한 호출의 최종 Tool 인자와 required_condition만 본다.
- R은 여기에 두 가지를 더한다: 지원 불가·확인 요청이 기대인데 답한 문항(Tool 인자에 남지 않는 요구), 기본값으로 바뀐 승하차 기준.

## 5. 운영 판단 기준 (실행 전 고정)

각 기준은 표시 문항을 포함한 값과 뺀 값 모두에서 성립해야 한다.

| | 기준 |
|---|---|
| OP1 운영 조건에서도 B보다 낫다 | 각 순서 k(W1–W3)에서 T2PC Wk와 B Wk가 v13 F1–F4를 충족한다: U ≤, 조용한 오답 ≤, 정상 ≥, 조건을 버린 답 ≤. 추가로 U∪R ≤ |
| OP2 연속 실행에서 품질이 유지된다 | T2PC의 각 Wk가 T2PC C1 대비 다음을 충족한다: 정상 ≥ C1 − 3, 조용한 오답 ≤ C1 + 1, U∪R ≤ C1 + 1, 조건을 버린 답 ≤ C1 |
| OP3 질문 사이 누출 없음 | 모든 run의 요청에서 다른 질문의 내용이 들어간 요청 0 |
| OP4 비용 | T2PC W run의 실패한 LLM 호출 0, 지연 중앙값 ≤ C1 |

**판단 규칙(결과를 본 뒤 완화하지 않는다):**
- **모두 충족:** T2PC를 유지한다. 검증 범위에 "연속 실행(순서 3개, 56문항)"을 더하고 측정 범위를 문서에 적는다.
- **OP1 불충족(어느 순서에서든):** 운영 조건에서 B보다 낫다는 근거가 무너진 것이다. 조합 전체를 되돌린다(`git revert -m 1 b62f6dc`).
- **OP1 충족, OP2 불충족:** T2PC는 유지한다(운영 조건에서도 B보다 낫다).
  - 다만 문서의 품질 수치를 연속 실행 범위로 바꾸고, v13 수치가 연속 사용을 대표하지 않는다고 적는다.
  - 문항마다 모델을 내리는 실행 옵션은 추가하지 않는다. 적재 직후 상태가 더 올바른 상태가 아니고, 27b는 적재에 질문마다 약 8초가 든다.
- **OP3 불충족:** 구현 오류다. 고친 뒤 해당 run을 다시 재고, 수정 전후를 나눠 보고한다.
- **OP4 불충족:** 원인을 기록한다. timeout이면 timeout 설정이 아니라 원인(생성 길이 등)부터 확인한다.
