# 실제 사용할 조합의 완성: 조건 계층 공통 코드와 측정값 추출 (grounding_v12)

작성: 2026-10-05. **grounding_v11 결과를 본 뒤 만든 기준이다.** 새 최종 검증 셋(`final_questions.yaml`)의 결과를 보기 전에 고정하며,
그 결과를 본 뒤 완화하지 않는다. grounding_v11의 "사전 등록 기준 미충족으로 미채택" 기록은 그대로 둔다.

## 1. 조건 계층 변경의 의미와 부작용 (기록 분석, 모델 호출 없음)

변경(`inherent_conditions`): 질문 표현("실차 택시")만으로는 측정값 정의가 이미 고정한 값(trip의 occupied)을 조건으로 채우지 않는다.

| 구분 | 내용 |
|---|---|
| 코드가 보장하는 사실 | schema상 get_trip_count·get_trip_metrics는 실차 구간만 다룬다. 측정값이 trip이면 occupied는 제한을 더하지 않는다. 조건 계층은 모델이 적은 값을 지우지 않는다. 공차·대기영업·받지 않는 택시 유형은 그대로 채워 그 이유로 멈춘다 |
| 모델 해석에 의존하는 전제 | 모델이 측정값을 trip으로 고른 것이 맞다. 코드는 이를 확인할 수 없다 |
| ① 모델의 최초 측정값 오독 | 통행량 질문을 trip으로 읽음(passage_to_trip). 기존 기록: qwen3:8b 7건, qwen3.8:27b(현재 설명·D·T2PC) 0건 |
| ② 조건 계층의 정당한 중복 조건 생략 | 측정값을 trip으로 맞게 읽은 "실차 택시가 태운 손님"류(s27–s29). 기존 코드는 occupied를 잘못 채워 부당하게 멈췄다 |
| ③ 변경 때문에 이전 오류가 실행까지 간 영향 | ①이 "실차 택시 통행량"처럼 occupied 표현과 겹치면, 기존 코드는 잘못 채운 occupied 때문에 우연히 멈췄고 새 코드는 잘못 읽은 trip으로 답한다. qwen3:8b 기록 재통과에서 2건(dev/037, old44/g04). 공차·대기영업 표현에서는 두 코드 모두 채우므로 생기지 않는다 |

- 기존의 잘못된 추가를 안전장치로 되살리지 않는다. 질문별 예외, 정규식 의미 보정, 모델명 분기도 두지 않는다.
- ③은 모델 선택의 문제로 남는다. 따라서 이 변경은 **모델·prompt·코드를 한 조합으로** 검증하고 채택한다. 다른 모델에서는 따로 잰다.
- **되돌리기:** 모델 이름만 바꾸면 새 코드·prompt에 qwen3:8b를 쓰는 검증되지 않은 조합이 된다(③의 위험 포함). 되돌리기는 코드·prompt·모델을 함께 되돌리는 것으로 정의하고 실제로 검증한다(5절).

## 2. 측정값과 반환 대상의 혼동 (기록 분석)

- **원출력:** dev/026·084, k25, m18, v10 held-out v06·v27(T2PC)
  - 그룹 기준(dimension·dimension_target)과 순위(order·limit)는 맞게 적었다.
  - 반환 대상인 장소("어디", "상위 2곳", "곳")를 MEASURE(LOCATION/place)로 두고, 세어야 할 trip 건수(또는 통행량)를 빠뜨렸다.
- **설명의 원인:**
  - MEASURE를 "질문이 구하려는 값"으로 정의하고 "구하려는 값이 장소명일 수도 있다"고 적었다.
  - 유일한 "어디" 예시(예시 5, scope 이름 묻기)의 MEASURE가 LOCATION/place다.
- **현재 표현의 충분성:** 무엇을 세나(MEASURE), 제한 조건(장소·factor), 묶는 기준(dimension·dimension_target·bucket),
  반환 대상(값 / order·limit로 고른 그룹 이름 / answer=bucket / 주어진 scope 이름)으로 모두 담을 수 있다.
  정답 grounding 실행기에서 확인했다. 새 필드는 두지 않는다.
- **첫 출력 측정값 오류(기록):**

| | 반환 대상을 측정값으로 | 통행량 → trip | trip → 통행량 |
|---|---|---|---|
| qwen3:8b(개발 320) | 1 | 7 | 2 |
| 27b+D(개발 320) | 1 | 0 | 0 |
| T2PC(개발+대조 353) | 4 | 0 | 1 |
| T2PC(v10 held-out 41) | 2 | 0 | 0 |

- **두 오류가 같은 원인이라는 가설은 지지되지 않는다.** 나타나는 모델과 형태가 다르다(반환 대상 혼동은 27b·T2, 통행량↔trip은 qwen3:8b).
  후보 설명이 qwen3:8b의 통행량→trip을 줄이는지는 따로 잰다(교차 모델 측정).

- 질문의 네 부분을 현재 표현에 대응시킨다.
  1. 무엇을 세거나 집계하나 → MEASURE

## 6. 작은 검증의 통과 기준 (27b 후보마다, 하나라도 미충족이면 그 후보 탈락)

- K1 측정값: 반환 대상을 측정값으로 읽은 첫 출력이 측정값 대조 R + 측정 실패 문항 + v10 held-out에서 합계 1 이하. 측정값 대조의 조용한 오답 0.
- K2 조건: 지원 불가(운행 상태 C 10 + n26 + 측정값 U 2)의 정확한 거부 ≥ 12/13. 모든 셋에서 조건을 버리고 답한 문항 0.
- K3 trip·OD: OD 대조 ≥ 15, 원인·측정 실패 19 중 정상 ≥ 16, 운행 상태 A·B·D·E 20 중 정상 ≥ 19.
- K4 일반 회귀(v10 held-out, 개발용): 조용한 오답 ≤ 1, 정상 ≥ 37.
- K5 조건 계층 훼손(잘못된 추가·삭제·놓친 채움) 0.

**두 후보가 모두 통과할 때의 선택 규칙.** T3PC는 다음 셋을 모두 만족할 때 고르고, 아니면 T3P를 고른다.
- (a) 위험 범위 확인: 27b + T3PC에서 통행량 + 실차 표현 문항(측정값 P 4, 운행 상태 s08, v10 held-out status_passage 중 occupied)의
  첫 출력 측정값이 모두 통행량이다.
- (b) T3P 기록을 T3PC 코드로 재통과해 거부에서 답(오답)으로 바뀐 문항이 0이다.
- (c) T3P가 멈추고 T3PC가 답하는 T형 문항(s27–s29, m17, m18)이 2 이상이다.

**둘 다 탈락하면** 전체 평가 없이 종료하고 기본값을 유지한다.

## 7. 제품 채택 기준 (X vs 기준 B = qwen3:8b + 522aa3b1 + 현재 코드)

중간 후보(T2PC, 다른 T3 후보) 대비 개선은 보고만 하고 채택 조건으로 쓰지 않는다. 기존 후보들의 최고 점수를 모두 넘을 것을
요구하지 않는다.

**품질(모두 충족):**
- A1 개발 311: 정상(X) ≥ 정상(B) + 10, 조용한 오답(X) ≤ 조용한 오답(B).
- A2 새 최종 검증: 정상(X) ≥ 정상(B), 조용한 오답(X) ≤ 조용한 오답(B), 정확한 거부(X) ≥ 정확한 거부(B).

**허용할 수 없는 회귀(하나라도 있으면 채택 안 함):**
- N1 X가 요구된 조건을 버리고 답한 문항 > 0(개발 지원 불가, 운행 상태·측정값 대조, 최종 검증 unsupported).
- N2 조건 계층 변경 때문에 X의 기록에서 거부가 답으로 바뀐 문항 > 0(X가 T3PC일 때, X 기록의 코드 재통과로 확인).
- N3 일반 회귀:
  - 최종 검증의 unsupported 밖 묶음에서 정상(X)이 정상(B)보다 2 넘게 낮다.
  - 개발 trip 밖 정상(X)이 정상(B)보다 3 넘게 낮다.
- N4 OD 대조 정상(X) < 11.
- N5 비용: 지연 중앙값 > 60초, 계획 호출 실패 문항 > 1%, GPU 3번(48GB) 하나에 적재 불가.
- N6 되돌리기 검증 실패.

**함께 보고하지만 채택 조건으로 쓰지 않는 것:** 실행 실패, 부당한 거부, 재질의 의존도, 호출 수, OD 층별, 측정값 오류 유형,
교차 모델(qwen3:8b + X) 결과, T2PC 대비 증감.

## 8. 결론의 형태

- **채택:** X(모델·prompt·코드·실행 설정)를 `geoflow/dev-v2`와 CLI GeoFlow 기본값·문서에 하나의 조합으로 반영한다.
  사용자 지정 `--model`·`OLLAMA_MODEL`·timeout 우선순위는 유지한다. 검증한 되돌리기 경로(태그 + 모델)를 문서에 남긴다.
- **미채택:** 기본값을 유지하고 무엇이 막았는지 적는다. 현재 아키텍처에서 해결 가능한 문제인지, 모델·계약·평가 자료 중 무엇이 더
  필요한지 판단한다. 한 문항 수정이나 새 held-out 생성을 다음 단계로 자동 제안하지 않는다.
