# 실차 구간과 운행 상태 조건 구분 사전 등록 (grounding_v10)

작성: 2026-10-04. 후보(T1)를 실행하기 전에 고정한다. 결과를 보고 바꾼 것은 끝의 "실행 기록"에 따로 적는다.

## 목표

qwen3.8:27b와 설명 D의 개선을 유지하면서 trip(실차 구간)의 의미와 별도 운행 상태 조건을 구분하게 하고, 그 결과로
제품 기본 조합의 교체 여부를 확정한다. 새 모델 탐색과 광범위한 prompt 조정은 하지 않는다.

## 확정한 원인 (grounding_v9 기록, 모델 호출은 thinking 확인 3건뿐)

- qwen3.8:27b + D의 trip 정지 24건(개발 15 + OD 대조 8 + held-out 1)은 모두 같은 사슬이다(`status_chain.py`).
  1. 모델: 측정값을 `AMOUNT/trip_count`로 맞게 고르고 같은 질문의 "실차"로 `taxi_status=occupied`를 함께 적는다.
  2. 조건 계층: 질문에 상태 조건 표현("실차 택시", "실차 통행량")이 없고 "실차" 단서만 있어 모델 값을 바꾸지도, 더하지도
     않고 보존한다(`held`, `unparsed_status_cue`).
  3. 합성: trip 계산에 이 조건을 받을 변환이 없어 `UNCONSUMED_CONDITION`(taxi_status)으로 멈춘다(부당한 거부).
- 같은 사슬이 n26("공차로 달리던 택시들의 평균 속도")에서는 질문이 요구한 조건을 보존해 정당하게 멈춘다. 코드 경로가 아니라
  모델이 대상의 뜻을 별도 조건으로 다시 적는 것이 문제다.
- 왜 적는가(thinking 원문, `think_D.jsonl`): m10에서 모델은 통행량 항목 안의 문장 "실차·공차·대기영업은 taxi_status 조건입니다"와
  "'실차 구간 건수'만 AMOUNT/trip_count입니다"를 인용하고, "trip 맥락에서 실차는 occupied(공차와 구별)"라고 판단해 trip에도
  조건을 붙인다. 같은 모델이 c02a("출발한 실차의 도착 읍면동")에서는 "실차 = trip"으로 읽어 붙이지 않는다.
  - 판단: 통행량 규칙을 trip으로 **확장**한 것이다. 지시끼리의 정면 충돌은 아니다. 그 문장이 통행량 범위로 적혀 있지 않고,
    prompt 어디에도 "trip은 정의상 실차"나 "taxi_status를 받는 측정값은 통행량뿐"이 없다(factor 의미는 "운행 상태 조건."뿐).
  - "'실차 구간 건수'만 trip_count"는 정확한 문구가 아닌 "실차"를 상태 단어로 읽을 여지를 만든다.
- 실행 계약(`schemas/tims.yaml`): `taxi_status`를 받는 Tool은 `get_passage_count`뿐이다. `get_trip_count`·`get_trip_metrics`는
  `taxi_status`와 `taxi_type`을 받지 않는다.
- "조건을 빼면 정답 grounding과 같다"(v9 `status_attribution.py`)는 원인 진단에만 쓰고 성과로 세지 않는다.
- 설명으로 바뀌지 않는 경로: 조건 계층은 "실차 택시"처럼 상태 단어 뒤에 "택시·통행량"이 오면 질문 표현으로 상태 값을 채운다.
  trip 질문에 이 표현이 오면 모델 출력과 무관하게 멈춘다. 기존 평가 셋의 trip 문항에는 이 형태가 없다(0건). 대조 셋 F(s27)로
  재고 따로 보고하며, 이번 작업에서 코드를 바꾸지 않는다.

## 후보 T1 (설명만, D 위)

1. trip 측정값 설명: 실차 구간은 손님을 태운 운행 한 번이며 그 자체가 실차다. "실차", "실차 구간", "손님을 태운 운행"이
   이 대상을 가리키면 trip이며 taxi_status를 따로 적지 않는다.
2. 통행량 혼동 쌍: "통행량에서" 실차·공차·대기영업은 taxi_status 조건이다. "'실차 구간 건수'만 trip_count"를 빼고, 실차 구간을
   세는 질문은 "구간"이라는 말이 없어도 trip_count라고 적는다.
3. `taxi_status` 의미: 받는 측정값은 통행량뿐이다. trip을 가리키는 '실차'는 조건으로 적지 않는다. 질문이 공차·대기영업 같은
   상태를 요구하면 측정값과 관계없이 적고, 받지 않으면 지원 불가로 멈춘다.

- 코드 경로(조건 계층·합성·검증)는 바꾸지 않는다. 새 필드, Tool 직접 선택, 질문 정규식, 조건 자동 삭제, 질문별·모델별 분기 없음.
- 평가 문장이 prompt에 들어가지 않게 예시는 일반 표현만 쓴다.
- 계약과 설명의 일치는 `tests/test_status_contract.py`가 지킨다(받는 측정값 = {passage_count}, 요구된 상태는 그 이유로 멈춤).
- **후보는 T1 하나다.** 탈락하면 문구를 다시 만들지 않고 기본값을 유지한 채 실패 기준과 남은 원인을 보고한다.

## 채택 기준

**설명 T1의 직접 효과 (T1 vs 27b+D, 개발 311 + OD 대조 + held-out):**
1. 개발 311 정상 답변 증가, 조용한 오답 비증가, 답해야 할 문항의 taxi_status 정지 감소.
2. D의 이득 보존: trip 밖 개발 정상이 3 넘게 줄지 않고, OD 실행 호출(장소 끝·묶는 끝 둘 다)이 줄지 않고, v8 OD 혼동 10건 정상(9)이 줄지 않는다.
3. 조건 보존: 지원 불가 문항(n26, 대조 C, held-out status_unsupported)에서 조건을 버리고 답한 문항이 27b+D보다 늘지 않고, 대조 C는 0.
4. held-out 정상 ≥ 27b+D, 조용한 오답 ≤ 27b+D.

**제품 기본 조합 교체 (T1 조합 vs qwen3:8b + 522aa3b1):**
1. 개발 311 정상 > 기준 + 3(반복 변동 0), 조용한 오답 ≤ 기준.
2. OD 대조 16 정상 ≥ 11.
3. held-out: 정상 ≥ 기준, 조용한 오답 ≤ 기준, 묶음마다 정상이 기준보다 2 넘게 낮지 않음, status_unsupported에서 조건을 버리고
   답한 문항 ≤ 기준.
4. 운행 상태 대조: C 조용한 오답 0, 전체 정상 ≥ 기준.
5. 비용: 지연 중앙값 ≤ 60초, 계획 호출 실패(timeout)로 끝난 문항 ≤ 1%, 48GB GPU 하나에 적재.

- 모두 충족하면 T1 조합(qwen3.8:27b + D + T1)을 기본 설정·문서에 반영하고 되돌리는 방법을 남긴다. 하나라도 미충족이면 현재
  기본값을 유지하고 실패 기준과 남은 원인을 보고한다.
- 결과는 이 실행 조합(모델 빌드·양자화·설정·prompt)의 효과로 보고한다. 모델 크기만의 인과 효과나 다른 환경의 재현성은 주장하지 않는다.

## 보고

최초 grounding, 조건 보존 뒤, 재질의 뒤, 최종 결과를 나누고 정상·정당 거부·조용한 오답·부당 거부·실행 실패를 따로 센다.
운행 상태 지표(정지, 조건 보존, 조건을 버린 답)와 재질의 의존도·지연·timeout·VRAM을 함께 보고한다.
