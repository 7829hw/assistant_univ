# 조건(날짜·장소·택시 유형) 보존

상태: 선택 기능으로 구현(`condition_check`, 기본 끔). 커밋하지 않은 작업 트리(HEAD `1229b53`).
구조화 집계 경로의 기본 활성화, TIMS 계약 완화, 모델 교체는 하지 않았다.

## 1. 이전 평가의 조건 오류 재분류

근거: `condition_error_audit_eval_v1.md`/`.json`(`condition_error_audit.py`로 생성).
기록된 LLM 원문을 재생해 첫 응답 → 최종 grounding → 실행 인자를 조건마다 이었다. 재생
결과는 기록된 결과와 60/60 일치했다. 집계 구조 오류는 세지 않았다.

**이전 보고의 "조건 누락 10건(두 경로 모두)"은 채점 오류를 포함한다.** 이전 채점기는
grounding 전체가 거부된 관측(`got None`)을 "조건 전부 누락"으로 셌다. 이런 관측은 flat 6건,
structured 3건이며, 조건을 판정할 수 없다.

| 유형 | flat | structured | 관측 |

| 질문에 있는 조건 누락: taxi_type | 3 | 1 | flat e01·e07·e29, structured e11. 모두 첫 응답부터 빠짐 |
| 질문에 있는 조건 누락: place | 0 | 1 | structured e02 |
| 조건 값·범위 변경 | 1 | 0 | flat e30 "8월 한 달 동안" → `20260801`(하루) |

| 날짜 형식 오류로 grounding 전체 거부 | 4 | 1 | "2026년 8월" → `202608`, "7월부터 8월" → `202607-202608`(flat e05·e08·e14·e19, structured e14) |

이 prompt는 고정된 실험 대상이므로 이번에는 바꾸지 않았다.

## 2. 설계

**선택한 방식: 규칙 기반 질문 해석(닫힌 어휘·문법)을 grounding 검증 앞에 둔다.**

| 방식 | 장점 | 단점 |
|---|---|---|
| 규칙 기반 질문 검사 | 호출 비용 0, 결정적, 누락과 추가를 모두 탐지(지원 표현 안에서) | 지원 문법 밖은 모름, 문장 구조가 필요한 의미는 판정 못함 |
| 구조화 추출 개선(근거 문자열 요구) | 근거 없는 추가를 찾기 쉬움 | prompt 변경(측정 필요), 누락은 못 찾음, 근거 문자열이 있어도 해석은 틀릴 수 있음 |
| 별도 LLM 검증 호출 | 표현 범위가 넓음 | 호출 비용, 검증기 자체 오류(V0 precision 0.71) |

실패의 대부분이 "지난달"·"개인택시"·"2026년 8월"처럼 닫힌 어휘로 읽히는 표현이었으므로 규칙
기반이 가장 작은 유효 변경이다. LLM 검증기는 만들지 않았다.

조건의 생애주기(`condition_audit`, `condition_trace`):

    질문의 근거 표현(mentions.text) → 해석된 조건(value, interpreted_range, 기준일)
      → 의미 graph의 적용 변환(applied_to) → 실행 인자(calls) → 답변의 "적용 조건" 줄

- 날짜와 택시 유형만 바꾼다. 개념 구조, 집계 표현(aggregation_plan), scope는 바꾸지 않고,
  끝에서 이를 확인한다.
- 바꾼 내역(`corrections`: from → to, action)을 남긴다. 한 번만 적용하며 재질의를 만들지 않는다.
- 조건이 의미 graph에 적용되지 않았거나 실행 인자에서 사라지면 실행 전에 멈춘다(`CONDITION_LOST`).
- 재질의 patch는 조건 기록과 집계 표현을 보존한다. 장소 값을 고치면 원래 근거와 수정 이력을 남긴다.

**문자열 존재와 해석의 구분.** 근거 표현이 질문에 있다는 것은 해석이 맞다는 보장이 아니다.
날짜는 코드가 문법으로 해석하므로 해석의 책임이 코드에 있다. 장소는 이름이 질문에 있는지만
보며, 그 장소가 분석 범위인지 출발지인지의 의미는 검증하지 않는다.

**누락 탐지의 범위.** 출력된 조건의 근거를 확인해도 누락은 찾을 수 없다. 누락은 질문 쪽을 읽어야
찾을 수 있다.

| 조건 | 누락 탐지 | 근거 없는 추가 탐지 | 확정 가능할 때의 처리 |
|---|---|---|---|
| 날짜 | 지원 문법 안에서 가능 | 날짜 단서가 전혀 없을 때만 | 코드 해석 값으로 채우거나 바꾼다. 모호·충돌·미지원은 확인 필요·지원 불가 |
| 택시 유형 | 지원 어휘 안에서 가능 | 유형 단서가 전혀 없을 때만 | 질문 표현으로 채우거나 바꾼다. 부정·여러 유형은 지원 불가 |
| 장소 | **불가** | 이름이 질문에 없을 때 | 확인 필요(`PLACE_NOT_IN_QUESTION`) |

지원 표현과 미지원·모호 표현의 목록은 `geoflow/conditions.py` 머리에 있다. 탐지하지 못하는 오류:
- 장소 누락
- 출발/도착 관계의 뒤바뀜(보존만 한다)
- 지원 문법 밖의 날짜 표현(단서가 있으면 LLM 값을 unverified로 둔다)
- 문장 구조가 필요한 택시 유형 표현

## 3. 상대 날짜의 결정적 해석

- 기준일은 주입된 clock(기본은 Asia/Seoul 오늘)이다. `seoul_date(instant)`는 시간대 있는
  시각만 받는다.
- last_week는 직전 달력 주(월~일), last_month는 직전 달력 월, last_year는 직전 달력 연도다.
  어제·오늘은 기준일로 계산한 `YYYYMMDD`다(단일 날짜는 계약으로 확인된 형식).
- 기록 항목: 원문 표현, 상대 의미, 해석 범위, 기준일, 시간대, LLM이 적은 값.
- TIMS 호출: 한 단계 집계는 기존처럼 상대 토큰(`last_month`)을 넘긴다. TIMS의 상대 날짜
  해석은 계약에 없으므로(`relative_date_reference` 알 수 없음) 답변은 코드의 해석 범위와
  "TIMS의 해석과 같다는 보장은 없음"을 함께 적는다. 구간별 집계는 기존처럼 코드가 푼 날짜로
  하루씩 호출한다. 기존 lowering 제한은 그대로다.
- "최근 한 달"≠"지난달", "최근 7일"≠"지난주": 앞의 것들은 지원하지 않음으로 돌려준다.
  pt_date에 해당 토큰이 없고, 범위 호출의 양 끝 포함 계약도 확인되지 않았기 때문이다.

## 4. 계약 보호(이전 보고 확인)

"계약 항목 값만 바꾸면 경로가 열린다"는 사실이었다. `ITEMS`의 status를 CONFIRMED로 바꾸면
근거 없이도 병합이 열렸다. 최소 보호 두 가지를 넣었다.

- CONFIRMED 항목은 출처 파일과 그 파일에 글자 그대로 있는 인용문을 가져야 한다.
  `evidence_problems()`를 테스트가 대조하므로, 근거 없이 올리면 테스트가 실패한다.
- 테스트 가정(`assuming()`)은 ASSUMED 상태로 표시하고, `allow_assumptions`가 참인 계약에서만
  인정한다. production pipeline에는 계약을 바꾸는 입구가 없다.

인용문이 있다는 것은 근거의 존재일 뿐 의미 동등성의 보장이 아니다. 그 판단은 항목을 올리는
사람의 몫이다.

  structured e20: 날짜가 맞아지자 지어낸 inner로 실행됨). 조건 계층은 집계 오류를 고치지 않는다.
- 다음 측정: 새 fresh 셋(다른 문장 틀과 지역 포함)에서 같은 사전 규칙으로 재측정하고, 채점기의
