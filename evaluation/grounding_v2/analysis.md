기존 기능이 막지 못한 이유는 하나로 모인다.
- 조건 계층은 날짜·택시 유형·운행 상태만 질문 원문과 대조했다. limit과 dimension_target은 **빈 값만 채웠다**.
- 장소 역할, 순위 방향, 집계, 답의 대상은 대조하지 않았다(`NOT_CHECKED`: "od_semantics: 보존만 함").
- 그래서 모델이 반대 값을 적거나 없는 값을 지어내면 그대로 통과했다(조용한 오답: 041·067·g11·g16·g40·g33·g32·g44).
- 모델이 값을 비웠을 때는 LLM 재질의가 조사 하나로 역할을 골랐다(041·067).

## 2. 현재 grounding 표현이 관계를 담는가

규칙을 더하기 전에 표현부터 봤다.

| 필요한 관계 | 현재 표현 | 판단 |
|---|---|---|
| 장소가 거르는 끝 | 장소 개념의 `od_role`(pickup/dropoff) | 충분 |
| 결과를 묶는 끝 | `dimension_target`(pickup/dropoff/both) | 충분. 거르는 끝과 따로 적힌다 |
| 같은 지역 안의 OD | 같은 값의 장소 개념 둘(pickup, dropoff) | 충분. 다만 실행이 같은 장소를 두 번 조회했다(채점기 v1이 이를 놓쳤다). 실행에서 조회를 한 번으로 바꿨다 |
| 순위 방향과 측정값 집계 | `order`/`limit`와 `aggregation` | 충분. 서로 다른 자리다 |
| 구간 안·구간 사이 집계 | `aggregation`/`rollup` | 충분 |
| 답의 대상이 구간(어느 주) | flat에는 **없음** | 부족. 구조화 표기(`aggregation_plan.result.select`)는 표현하지만 production은 flat이다 |

- 결론: 부족한 것은 표현이 아니라 **읽기와 대조**였다.
  - 모델이 관계를 비우거나 반대로 적는 것을 코드가 질문 원문과 맞춰 보지 않았다.
  - 답의 대상만 flat 표현에 자리가 없다.
- 이 경우는 새 LLM 필드를 만들지 않고, 코드가 질문 문형으로 읽어 flat 경로에서만 멈춘다. prompt가 바뀌면 무관한 문항의 출력이 변하므로(grounding_v1의 006·064) prompt는 바꾸지 않았다.
- 구조화 표기는 그대로 둔다. 구간 선택을 표현하고, 로컬 재계산 근거가 있으면 계산한다.

## 3. 선택한 개선

LLM은 grounding만 하고, macro 합성·typed graph·검증·컴파일·실행은 그대로다. 새 코드는 질문 원문과 grounding만 보는 조건 계층(`geoflow/relations.py`, `conditions.reconcile_relations`)이다. 문항 id·원문 전체 매칭·정답 조회·질문별 workflow는 없다.

### 3.1 무엇을 읽는가

| 관계 | 읽는 방법 |
|---|---|
| 장소 역할 | 장소 뒤의 **조사 + 서술어**. 조사 하나로 정하지 않는다. "부산에서 하차가 많은"은 dropoff, "수성구에서 출발한"은 pickup, "초량동으로 들어온"은 dropoff. "X에서 Y로/까지"는 X 출발·Y 도착. "X 안에서 … 노선/이동"은 같은 장소가 두 역할(개념 둘, 조회 한 번). 이동 문맥이 없는 "안에서"는 "에서"와 같다 |
| 묶는 끝 | 장소 역할에 쓰인 말을 떼고 그룹 단위에 붙은 말로 정한다("수성구에서 **출발**한 실차의 **도착** 읍면동"은 pickup으로 거르고 dropoff로 묶음). "간·노선·OD·승하차"는 both. 그룹 쪽에 말이 없으면 장소 역할을 정한 사건 명사(승차·하차)를 잇는다("부산에서 하차가 많은 읍면동") |
| 그룹 기준 | 단위 말(읍면동·시군구·시도·H3·요일)이 한 종류일 때(장소 이름은 가린다) |
| 순위 방향·개수 | 상위·하위·많은·적은·높은·낮은. 측정값 집계어(최대·최소·최댓값·"가장 큰 값")는 먼저 가린다. 개수 표현이 한 값이면 그 값, 없고 "가장"이면 1 |
| 집계 | 구간이 없으면 집계어가 한 종류일 때 그 값. 집계어도 단서도 없으면 "없음이 분명". 구간이 있으면 두 집계어는 앞이 구간 안·뒤가 구간 사이. 측정값 뒤의 집계어 하나는 구간 사이이고, 구간 안 집계는 질문에 없다 |
| 답의 대상 | "…가 가장 큰 주/달은?", "어느 주/달". 지역·요일 순위는 dimension으로 답할 수 있어 포함하지 않는다 |
| 측정값·사건 | 질문의 측정값 말이 한 계열일 때 대조한다. 같은 core concept·같은 사건이면 subtype을 바로잡는다. 빠진 측정값은 말과 모델이 적은 사건이 모두 맞을 때만 채운다. 확인된 측정값에 맞지 않는 암묵 사건은 맞춘다 |

### 3.2 누락·충돌·모호의 처리

| 질문 근거 | 모델 값 없음 | 모델 값 같음 | 모델 값 다름 |
|---|---|---|---|
| 분명함: 한 규칙이 한 값만 냄 | 채움 | 확인 | 바로잡음 |
| 반대 표현이 함께 있음(순위 방향, 묶는 끝) | 확인 요청 | 확인 요청 | 확인 요청 |
| 읽지 못함 | 그대로(기존 재질의가 맡음) | 그대로 | 그대로 |

- 생략이 Tool 기본값과 같으면 바꾸지 않고 `confirmed_equivalent`로 적는다. 예: 구간 없는 "평균" = avg, 묶는 끝 both.
- 근거가 없으면 지운다(`removed_no_evidence`):
  - 집계어도 단서도 없는 집계
  - bucket 없는 rollup
  - 출발·도착 서술어가 없는데 실차 구간 외 측정값의 장소에 붙은 역할
- 모든 보정은 `condition_corrections`에 남는다: 원문 근거(조각과 위치), 변경 전후 값, 적용 이유. 평가 기록의 행마다 들어 있다.
- 모든 충돌을 덮어쓰지 않는 장치:
  - 분명함의 조건은 서술어까지 맞는 문형이다. 조사만 맞는 것은 분명함이 아니다.
  - 반대 표현이 있으면 고르지 않는다.
  - 모두 확인 요청으로 보내지 않는 장치: 분명한 충돌은 바로잡는다. 064처럼 같은 계열의 측정값 변동도 확인 요청 대신 바로잡는다.
- 잘못된 보정의 점검: 업체 100·기존 44·대조 사례의 정답 grounding 173개를 넣으면 아무것도 바뀌지 않는다(`tests/test_relations.py` GoldSilenceTest). 이 규칙들은 정답의 다음 항목을 모두 확인했다:
  - 역할 70
  - dimension 63
  - dimension_target 36
  - order 63
  - limit 63
  - 집계 74
  - rollup 16

### 6.4 보정 전 모델 출력과 보정 후 grounding의 차이

최종 후보 실측 255행(다섯 셋) 가운데 70행에서 관계 보정이 작동했다(날짜·택시 유형·운행 상태 제외). 종류별:

| 보정 | 건수 |
|---|---|
| od_role 채움 / 바로잡음 / 제거 | 37 / 1 / 1 |
| limit 채움 / 바로잡음 | 11 / 1 |
| aggregation 채움 / 근거 없어 제거 | 3 / 17(모두 개수 Tool의 집계이거나 구간 안 집계) |

| dimension 채움 / 바로잡음 | 1 / 3 |
| dimension_target 채움 / 바로잡음 / 제거 | 4 / 1 / 4 |
| order 채움 / 바로잡음 | 3 / 2 |
| measure 채움 / 바로잡음, event 바로잡음, bucket 제거 | 1 / 1, 1, 1 |

모든 행이 근거 표현(원문 조각과 위치), 이전 값, 이후 값, 이유를 가진다. 모델 원 출력은 `llm_calls[0].content`, 보정 뒤 grounding은 `grounding`이다.
