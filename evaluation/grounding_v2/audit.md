# grounding_v1 평가 기록의 정합성 점검

작성: 2026-09-29. 원시 기록(`evaluation/grounding_v1/runs/*.json`)과 채점기(`evaluate_vendor100.py`)로 문항마다 포함 여부,
제외 이유, 기대 결과, 실제 결과를 다시 확인했다. 문항별 표는 `v1_records_rescored.md`(채점기 v2로 다시 채점,
`evaluate_vendor100.py report --items`).

## 1. 지난 보고의 불일치

원시 기록의 범주 합계는 모두 분모와 같았다(업체 100: 100, 기존 44: 44). 불일치는 보고에서 범주를 옮겨 적을 때
생겼다.

## 2. 064: "정답"으로 채점됐는데 "그대로 답하면 오답"인 이유

서로 다른 두 실행의 이야기를 한 문장에 섞었다. 채점 오류는 아니다.

- B0(`b0_qwen3_8b.json`): 모델이 "RPM 중간값"을 `rpm`으로 적었다. 호출 `get_passage_metrics(metric=rpm, aggregation=med, …)`이
  업체 정답과 같아 정상 답변이다.
- prompt 변경(두 단계 집계 규칙 추가, sha 238ac8d6) 뒤: 같은 질문에 모델이 `speed`를 적었다(무관한 문항의 출력 변동).
  - 가드가 없던 후보 C3c(`final_dev_qwen3_8b.json`)는 `metric=speed`로 답해 오답이다(인자 차이 `metric rpm→speed`).
  - 최종(C3d)은 측정값 말 충돌 가드로 확인을 요청했다(부당한 거부).
- 그래서 "그대로 답하면 오답"은 prompt 변경 **뒤**의 모델 출력에 대한 말이다. B0의 정상 답변은 의미로도 맞다.
- 이번 변경에서는 같은 사건 계열의 측정값끼리(speed↔rpm)는 질문의 말로 바로잡는다. 재생에서 064는 정상 답변이 된다.

## 3. 답변 성공과 의미 정답을 섞은 채점이 있는가

채점기의 "정상 답변"은 다음을 모두 요구한다.

- 호출: Tool, 인자(기본값 정규화 뒤), 장소 조회, 분석 호출 1회
- scope: 장소 조회 결과에서 온 것
- 답변: Tool 반환값이 그대로 들어 있음

그러므로 "답했다"만으로 맞음이 되지는 않는다. 확인한 것과 찾은 것은 다음과 같다.

**채점 오류 1건(수정, 채점기 v2).**
- v1은 장소 조회를 집합으로만 비교해, 같은 장소를 두 번 조회해도 맞음으로 셌다.
- 업체 정답 093·095(`$area.scope`)는 한 번 조회한 scope를 출발·도착에 함께 쓴다.
- v2는 조회 횟수까지 비교한다. 영향은 정답 grounding 층뿐이다.
  - 업체 100: 100 → 98(093·095)
  - 기존 44: 41 → 40(g14)
- LLM 실행 기록에는 이 경우 맞음으로 센 행이 없었다(해당 문항은 모두 다른 이유로 틀렸다).
- 코드도 고쳤다. 같은 인자의 장소 조회는 한 실행 안에서 한 번만 부르고 결과를 다시 쓴다(`executor.REUSABLE_LOOKUPS`).

**호출은 같지만 grounding 의미가 다른 행(채점 오류 아님, 따로 보고).**
- B0 002·056과 최종 009·056·072·g01은 호출이 정답과 같아 정상 답변이다.
- 그런데 grounding에는 질문에 없는 `aggregation=sum`이 들어 있다.
  - 개수 Tool은 집계 인자를 받지 않으므로 계산은 같다.
  - 답변 문장에는 "합계"가 붙는다.
- 호출 정확도는 맞음, grounding 정확도는 틀림으로 두 지표에서 이미 따로 셌다.
- 이번 변경은 질문에 집계어도 단서도 없는 집계를 지운다.

**기대 거부의 이유.**
- 사전 등록은 결과 종류(unsupported / needs_clarification)만 채점했다.
- 기록의 정당한 거부는 모두 의도한 이유였다: g17 UNCONSUMED_CONDITION, g44 AMBIGUOUS_INNER_AGGREGATION(정답 grounding 층).
- 보고서에 거부 코드를 함께 적는다.

**표기의 약점: 장소 두 개의 역할이 조회 순서로 정해진다.**
- 업체 gold 표기는 `$pickup`/`$dropoff`를 get_place_scope의 순서로 묶는다.
- 순서를 뒤집어 적으면 정답이 역할을 뒤집는다.
- 정답 grounding 역산도 같은 순서를 따르므로, 정답 grounding 층 점검으로는 드러나지 않는다.
- 새 독립셋 n08이 그랬고, LLM 실행 전에 고쳤다.
- 업체 100·기존 44·대조 사례에서는 관계 읽기 규칙이 정답 grounding의 역할 70개를 모두 질문 문형과 같다고 확인했다(`tests/test_relations.py` GoldSilenceTest). 뒤집힌 라벨은 없다.

## 4. 호출·지연 기록

**숨은 timeout.**
- v1 평가기는 실패한 LLM 호출(timeout 등)을 기록하지 않았고, planner는 같은 요청을 다시 불렀다.
- 그래서 지난 보고의 "호출 122 → 113"에는 timeout 난 호출이 빠져 있다.
- 기록된 호출 시간 합과 문항 전체 시간의 차이가 timeout(300초)에 가까운 문항으로 추정했다:
  - 업체 100: B0 1(044), 최종 4(041·044·067·100)
  - 기존 44: B0 1(g12), 최종 0
- v2 평가기는 실패한 호출을 `llm_calls`에 `failed`로 남긴다.

**p90.**
- 지난 보고의 p90(25.0 / 20.9초)과 계산 방식이 달랐다.
- 보고서는 최근접 순위 백분위수로 통일한다. 같은 기록에서 24.2 / 20.7초다.
- 긴 지연을 빼지 않는다.

**전체 경과 시간.**
- v1 기록에는 없다. meta.started_at은 이어 실행했을 때 마지막 조립 시각이고, 파일 시각은 복사 시각이다.
- v2는 문항마다 started_at / finished_at을 남긴다.

## 5. 성능 변화와 원인 귀속

- 관측된 변화: 같은 채점기로 센 전후 차이다. 프롬프트 변경으로 간접적으로 좋아진 문항도 채점 기준을 충족하면 여기에 들어간다. 기존 44의 22 → 36에는 g24·g28·g29·g31·g35·g38이 포함된다.
- 원인 귀속: 특정 규칙이 작동했다는 기록이 있을 때만 그 규칙의 효과로 적는다. 위 여섯 문항은 최종 원 출력에서 해당 형태가 사라졌을 뿐 어떤 규칙도 작동하지 않았다. 그래서 "관측된 개선이지만 원인은 prompt 변경에 따른 출력 변동"으로 적는다. 같은 종류의 변동이 업체 006·064에서는 반대 방향으로 나타났다.
- 이번 단계의 보고도 이 둘을 나눈다. 행마다 `condition_corrections`(근거 표현·전후 값·이유)를 남겨, 어느 규칙이 작동했는지 기록으로 확인할 수 있게 했다.
