## 2. 유지한 계약과 바꾼 복구 책임

**유지:**
- flat grounding 계약과 `answer`(value|bucket)
- 집계 IR(`from_flat`의 UNSPECIFIED)
- 기본 prompt(522aa3b1)
- 조건 계층
- 재질의 1회 예산
- 구간 안 집계 미지정은 재질의하지 않는다(모델이 집계를 지어내는 경로를 열지 않는다)
- 원문 정규식 재해석은 되살리지 않았다

**바꿈 (`geoflow/repair.py`, `geoflow/planner.py`, `geoflow/pipeline.py`, 재질의 문구):**

1. **factor 수정 재질의.** factor 계약 오류를 결과 형태 factor 안에서 고친다. 대상 오류는 짝 누락, `INVALID_ANSWER_TARGET`, 결과 형태 factor와 시간대의 `INVALID_FACTOR`다.
   - 결과 형태 factor(`RESULT_SHAPE_FACTORS`): bucket, aggregation, rollup, answer, dimension, dimension_target, order, limit.
   - 기간·택시 유형·운행 상태·장소 등 개념은 바꿀 수 없다. 파서와 delta guard가 거부한다.
   - 코드는 의미상 정답을 정하지 않는다. 수정 범위와, 수정 결과가 grounding 계약·합성·검증·컴파일을 처음부터 다시 통과하는지만 본다.
2. **수정안 형식.** 수정안은 "고친 뒤의 수정 범위 전체"다.
   - 처음(R)에는 바뀐 것만 적게 했다. 그런데 범위 위반 7건 중 5건이 모델이 전체를 적으면서 잘못된 조건을 빠뜨린 것이었다. 그래서 모델이 실제로 쓰는 형식에 맞췄다.
   - 옛 prompt 고정 변형(`evaluate_prompt_ab.py`)은 옛 문구와 적은 것만 바꾸는 방식을 유지한다.
3. **재질의 문구.**
   - 집계 재사용 지침을 뺐다.
   - 한 집계어는 한 단계에만 쓰고, 구간 안 집계 표현이 없으면 aggregation을 적지 않는다.
   - 계약에서 만든 해결 방법을 보여 준다(`describe_resolution`). 예: "answer는 bucket이 있을 때만 쓸 수 있습니다. 질문에 bucket에 해당하는 표현이 있으면 채우고, 없으면 answer를 뺍니다". 질문은 읽지 않는다.
4. **계획 단계 오류.** grounding 계약에서 멈춘 첫 응답을 초안(`PlanningDraft`)으로 붙여, 합성 단계와 같은 판정(`repair.decide`)으로 재질의한다.
5. **그룹 보존 guard.** 수정은 그룹을 계약에 맞게 적는 방법을 고치는 것이다. bucket/dimension을 모두 없애는 수정은 거부한다.
   - R2 재생에서 계약에 없는 bucket=hour("시간대별로")를 빼고 전체 합계로 답한 수정(m40)이 조용한 오답을 만들어서 넣었다.
   - 최종 실측에서는 n23("달별로 나눠 봤을 때")의 같은 형태 수정을 막았다.
6. **질문에 정보가 없을 때.** 모델이 `{"unsupported": true}`로 답하면 둘로 나눈다.
   - 빠진 짝·답 대상: 사용자 확인(needs_clarification)
   - 계약에 없는 값: 지원 범위 밖(UNSUPPORTED_QUESTION)
7. **추적.** 시도 기록에 최초 오류, 수정안 원문(`repair_raw_text`), 수정 뒤 factor(`repaired_factors`), 재질의 실패 이유(`repair_error`)를 남긴다.

## 6. 올바른 입력의 회귀와 수정 범위 보존

- **정답 grounding → 실행기:** 7개 셋 모두 grounding_v4와 결과가 같다(`gold/`). 올바른 grounding은 재질의 없이 그대로 실행된다.
- **층별(`layers_final.md`):**
  - 형식 정규화·조건 보존의 훼손은 0이다.
  - 재질의 전 → 최종 grounding은 고침 33, 훼손 2다. 065와 n14에서 수정안이 요일 순위에 bucket=week를 넣었다. 결과는 C와 같이 실행 실패다.
- **수정 범위:**
  - 최종 실측의 factor 재질의 24건 중 범위 위반 거부는 4건이다: n23 그룹 삭제, m40 그룹 삭제, g24 변화 없음, 095 관계 재질의 중복 지정.
  - 기간·택시 유형·운행 상태·개념을 바꾼 수정은 적용된 것이 0건이다.
  - 재질의가 끝나기 전에 Tool을 부른 경우는 없다(재질의 실패 문항의 Tool 호출 0).
- **코드 행동 검증(`tests/test_factor_correction.py`, 모델 없음):**
  - 요일 순위 answer 빼기, 집계어 옮기기 → 확인 요청
  - 범위 밖(기간·유형) 변경 거부와 Tool 미실행
  - 재수정 금지(재질의 1회)
  - 계획 단계 `INVALID_FACTOR` 재질의, 날짜 값 오류는 재질의하지 않음
  - 그룹 삭제 거부
  - 값/구간 질문의 무재질의 실행
  - 짝 규칙마다 재질의 문구의 수정 범위 = 파서의 수정 범위이고, 수정 결과는 합성을 다시 지난다
  - 이것은 코드가 할 수 있다는 검증이다. 모델이 올바른 수정안을 내는지는 위 실측 수치다.

## 7. 남은 한계

- **첫 grounding의 집계 발명**(t02c, t05b, m24): 검증에 걸리지 않는 의미 오류다. 모델 해석 개선 없이는 해결되지 않는다.
- **재질의가 새 의미 오류를 만드는 경우:** g44(aggregation 발명), c06a(순위 삭제). 범위 guard는 그룹 삭제만 막는다.
- **answer 오용 복구율이 낮다**(3/15). 실패는 모두 실행 전 멈춤이다.
- **재질의 출력이 실행마다 흔들린다:** 같은 코드에서 R2g 재생 236, 실측 232.
- **재질의 예산 1회:** factor 수정 뒤 관계 재질의가 필요한 문항은 멈춘다(최종 007, P 후보에서 6건). 예산은 늘리지 않았다.
- **기본 prompt 짝 지침 모순은 남아 있다.** 고친 변형은 7개 셋 −10이라 되돌렸다. 관측된 실제 피해는 없었다.
- **일반 질문 회귀:** 업체 100 87(기준 93), 기존 44 28(기준 36). grounding_v4 prompt 변경의 첫 응답 변화이며 이번 작업 범위에서 되찾지 못했다.
- **연도 없는 날짜:** 기존 확인 요청 정책을 유지했다. k01·k04·k16은 그대로 부당한 거부로 센다.
- **평가 범위:** 모든 셋이 개발셋이다. 문항 몇 개 차이는 일반 오류율이 아니다.

## 8. 재현

```bash
PY=python; S=evaluation/grounding_v5; source $S/sets.sh
$PY -m unittest discover -s tests -t .
for s in $SETS; do $PY evaluate_vendor100.py --gold ${GOLD[$s]} gold --out $S/gold/$s.json; done
# 복구 경로만(C의 첫 응답 재생, 재질의는 실제 모델)
for s in $SETS; do $PY evaluate_vendor100.py --gold ${GOLD[$s]} llm --model qwen3:8b --condition-check \
  --replay-from evaluation/grounding_v4/runs/final_${s}_qwen3_8b.json --out $S/replay_R2/$s.json; done
# 기록 응답을 이 코드로 다시 적용(모델 호출 없음)
for s in $SETS; do $PY evaluate_vendor100.py --gold ${GOLD[$s]} rerun $S/replay_R2/$s.json --out $S/rerun_R2g/$s.json; done
# 전체 격리 실측
for s in $SETS; do $PY evaluate_vendor100.py --gold ${GOLD[$s]} llm --model qwen3:8b --condition-check --out $S/runs_final/$s.json; done
$PY $S/counts.py final=$S/runs_final        # 결과 분류·집계 발명·answer 오용·재질의

```
