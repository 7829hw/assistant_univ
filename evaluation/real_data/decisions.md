# 실제 자료 검증 전에 정해야 할 해석 (결정표)

작성: 2026-10-05(grounding_v15), 근거 수준 정정: 2026-10-05(grounding_v16).

- 업체나 서비스 담당자가 정해야 할 의미를 여기서 확정하지 않는다.
- 사람 검토 없는 합성 라벨을 업체 정답으로 바꾸지 않는다.
- 이 근거 정리로 기존 평가 라벨이나 채택 판정을 소급 변경하지 않는다.

각 결정은 네 층으로 나눠 적는다.

| 층 | 뜻 | 인정하는 근거 |
|---|---|---|
| 업체 문서 | 업체가 문장으로 명시한 정의 | `schemas/*.yaml`, `prompts/system.yaml`(업체 제공 prompt), README "업체 v2"(업체 제공 v2 파일 반영, ebb9bc3). 확인 상태는 `geoflow/tims_contract.py`의 CONFIRMED·OBSERVED·UNKNOWN을 따른다 |
| 프로젝트 해석 | 프로젝트가 채택한 해석·기본값 | `geoflow/factors.py`(모델에 알리는 계약), `geoflow/measures.py`(측정값별 집계 의미의 프로젝트 판단), 라벨 정책 |
| 코드 동작 | 코드가 허용하거나 막는 것 | validator·compiler·measures의 실제 분기 |
| 미확인 | provider가 실제로 무엇을 계산하는지 아직 모르는 부분 | `tims_contract.py`의 OBSERVED·UNKNOWN 항목, 문서에 없는 의미 |

`measures.py`의 설명은 프로젝트 판단이다. 업체 계약의 확인으로 보지 않는다.

각 결정의 `상태:` 줄은 `validate.py`가 읽는다. 값은 `미결정` 또는 `결정됨(근거 위치)`이다. 미결정 항목을 `vendor_decision` 근거로 인용하면 검사에서 오류가 난다.

## D1 수입이 가장 많은 요일

- 상태: 미결정
- 질문 예시(합성, 검토 없음): m05 "이번 달 택시 수입이 가장 많은 요일은 언제야?", m08, f08 "지난달 택시 하루 수익금이 가장 높았던 요일"

| 층 | 내용 |
|---|---|
| 업체 문서 | `get_billing_metrics`: "일 단위 택시 영업(operation) 관련 통계값", `revenue=1일 수익금`, `dimension=dayofweek`(scope 없이 가능)(schema). aggregation 기본값 avg(CONFIRMED `aggregation_default`) |
| 프로젝트 해석 | 질문에 집계어가 없으면 aggregation을 적지 않는다(factors). 생략 시 답변에 "TIMS 기본값(평균)이 적용"을 고지한다(answer). revenue는 "택시·일 기록의 금액"이고 모든 집계를 허용한다(measures, 프로젝트 판단) |
| 코드 동작 | sum·avg·max·min·med와 dayofweek를 허용한다. 집계어가 없으면 생략한 호출이 나간다 |
| 미확인 | avg의 분모(원시 단위: 택시·일인지 등, OBSERVED `inner_avg_unit`). 기간 집계가 택시·일 기록에 바로 적용되는가(OBSERVED `day_records:get_billing_metrics`). 자료 없는 날(UNKNOWN `null_result`). this_month가 기준일까지인지(UNKNOWN `relative_date_reference`) |

가능한 해석과 표현 여부:

| 해석 | 단일 Tool 호출 | 현재 GeoFlow 계약·컴파일러 | 확인된 계약이 있을 때 로컬 합성 |
|---|---|---|---|
| (a) 요일별 기간 총수입 | `aggregation=sum, dimension=dayofweek` | 표현됨 | – |
| (b) 기본값 avg 그대로 | 생략 또는 `aggregation=avg` | 표현됨. avg가 무엇의 평균인지는 미확인이다. "택시 한 대의 하루 평균"은 프로젝트의 읽기다 | – |
| (c) 날짜마다 전체 수입을 구한 뒤 그 요일의 날짜들로 평균 | 불가. billing의 bucket은 week·month뿐이다. dimension+aggregation은 기록에 집계 하나를 적용할 뿐 "날짜별 합의 요일 평균" 인자가 없다 | 불가. 집계 IR의 구간은 week·month뿐이고(`aggregation.BUCKET_LABELS`), 날짜 구간을 요일로 묶는 표현이 없다 | 원리상 가능하다. 날짜마다 sum 호출 → 요일별 평균. 단 `single_date`(CONFIRMED) 외에 `day_records:get_billing_metrics`(OBSERVED)와 `null_result`(UNKNOWN)가 확인되어야 하고, GeoFlow에 그 표현과 컴파일 경로를 새로 만들어야 한다. 지금은 구현하지 않으며 계약도 추정하지 않는다 |

- **답변 차이:**
  - (a): 한 달 안에서 요일마다 날짜 수가 4·5로 달라, 5번 있는 요일이 유리하다.
  - (b): 분모가 확인되지 않아 값의 뜻을 단정할 수 없다.
  - (c): 날짜 수 차이를 없앤 비교다.
- **물을 것:**
  - 기본 해석은 (a)·(b)·(c) 중 무엇인가?
  - (b)의 avg는 무엇의 평균인가? 업체 계약 답이 필요하다.
  - (c)가 기본이라면 계약에 그 계산을 추가할 것인가, 로컬 합성 근거(날짜 귀속·자료 없는 날)를 줄 것인가?
  - 집계어 없는 질문에 기본값을 쓰고 고지하는 지금 방식을 유지할 것인가?

## D2 운행일 지표

- 상태: 미결정
- 질문 예시: f10 "작년 법인택시 운행일 지표가 높은 시도 상위 두 곳은?"

| 층 | 내용 |
|---|---|
| 업체 문서 | `operating_days=운행일`(schema). "operating_days는 분석기간 동안 택시별 운행일수를 구한 뒤 대상 택시 전체에 집계하는 metric"(README 업체 v2). aggregation 기본값 avg(CONFIRMED) |
| 프로젝트 해석 | "운행일 지표"를 operating_days로 읽는다(모델의 grounding). 집계어가 없으면 aggregation을 적지 않는다. operating_days는 택시별 기간 집계이고 하루 값들로는 sum만 다시 만들 수 있다(measures, 프로젝트 판단) |
| 코드 동작 | 모든 집계를 인자로 허용한다. 하루 분할 합성은 sum만 허용한다 |
| 미확인 | "대상 택시 전체에 집계"의 대상: 운행일 0인 택시를 분모에 넣는가? 기간 경계(작년=1–12월?, `relative_date_reference` UNKNOWN). avg가 택시당 평균인지는 업체 v2 문장에서 읽히지만 분모 정의는 없다 |

| 해석 | 표현 |
|---|---|
| (a) 택시당 평균 운행일(avg, 기본값) | 표현됨. 분모(대상 택시)는 미확인 |
| (b) 총 운행일(택시·일 합, sum) | 표현됨 |

- **답변 차이:** (b)는 차량이 많은 시도가 위로 간다. (a)는 차량당 가동 정도다.
- **물을 것:**
  - "운행일 지표"의 기본은 (a)인가 (b)인가?
  - (a)의 분모에 운행일 0인 택시가 들어가는가?

## D3 한 달 동안 활성 택시 수

- 상태: 미결정
- 질문 예시: f16 "2026년 8월 한 달 동안 서울의 활성 택시 대수는 몇 대였습니까?"

| 층 | 내용 |
|---|---|
| 업체 문서 | "활성택시: 1일 기준으로 영업 행위를 한 택시"(system). `active_taxi_count=활성택시 댓수`(schema). aggregation 인자는 avg·max·min·sum·med를 받는다(schema enum). 기간에 걸친 활성 대수의 정의는 없다 |
| 프로젝트 해석 | 하루 정의만 있으므로 날마다의 대수를 더하면 택시·일이 되어 고유 대수가 아니다. 그래서 sum은 뜻이 정해지지 않은 집계로 본다(measures, 프로젝트 판단). avg·max는 막지 않는다 |
| 코드 동작 | sum은 `UNDEFINED_MEASURE_AGGREGATION`으로 멈춘다. avg·max·min·med는 호출한다. 집계어가 없으면 기본 avg 호출이다 |
| 미확인 | 기간 조회에서 avg·max가 무엇을 계산하는지(날마다의 활성 대수의 평균·최대인지 등)는 업체 문서에 없다. schema가 인자를 받는다는 사실은 기간 집계의 의미가 확인됐다는 뜻이 아니다 |

| 해석 | 표현 |
|---|---|
| (a) 날마다의 활성 대수의 평균 | 인자(avg)는 있다. 그 계산이 이것인지는 미확인 |
| (b) 그 달에 한 번이라도 영업한 서로 다른 택시 수 | 불가. 기간 고유 대수를 세는 인자·정의가 없다 → 지원 불가로 멈춰야 함 |
| (c) 날마다의 활성 대수의 최대 | 인자(max)는 있다. 그 계산이 이것인지는 미확인 |

- **답변 차이:** (b)는 (a)보다 크거나 같다. (b)를 avg로 답하면 사용자가 원한 값이 아니다.
- **물을 것:**
  - "한 달 동안 활성 택시 수"는 (b)를 뜻하는가?
  - 기간 조회에서 avg·max는 무엇을 계산하는가? 업체 계약 답이 필요하다.
  - (b)가 기본이면 지원 불가로 안내할 것인가, 새 지표를 계약에 추가할 것인가?

## D4 지역 없는 지명

- 상태: 미결정
- 질문 예시: f28 "지난주 중구에서 수성구로 이동한 운행을 출발한 동 기준으로 보면 가장 많은 동 두 곳은 어디예요?"

| 층 | 내용 |
|---|---|
| 업체 문서 | "동일 명칭의 장소가 여럿인 경우 후보 목록을 반환한다"(gazetteer `get_place_scope`). region: "발화에 없으면 빈 문자열로 두고 임의로 추정하지 않는다"(gazetteer). "모호한 경우 도구가 후보 목록을 반환하므로 그 결과를 근거로 재질의합니다"(system) |
| 프로젝트 해석 | 같은 정책을 따른다. 모델은 region을 비우고, 다른 장소 단서로 지역을 추론하지 않는다 |
| 코드 동작 | mock gazetteer에는 "중구"가 대구 중구 하나뿐이다. 후보 목록 응답은 mock에 없어 GeoFlow가 그 응답을 어떻게 처리하는지 실행된 적이 없다 |
| 미확인 | 실제 후보 목록 응답의 형식(필드·순서·개수). 그 응답에서 GeoFlow가 확인 요청으로 가는지 |

- **기준이 되는 동작:** 지역 추정 금지와 후보 확인(재질의)이다. 이것이 현재 계약이다.
- **두 종류의 일을 구분한다.**
  - 계약 확인: 업체에서 후보 목록 응답의 실제 형식을 받아, GeoFlow가 그 응답에서 확인 요청으로 가는지 확인하는 일이다.
  - 제품 결정: 다른 장소 단서(예: "수성구"는 대구에만 있음)로 지역을 좁히는 것은 정책 변경이다. 서비스 담당자가 따로 결정해야 하고, 결정되기 전에는 하지 않는다.
- **답변 차이:** 추론이 틀리면 다른 지역의 운행을 센다. 이는 잘못된 scope이며 용납할 수 없는 실패다.
- **물을 것:**
  - 실제 후보 목록 응답 형식은 무엇인가? (계약 확인)
  - 다른 장소 단서로 좁히는 정책 변경을 원하는가? (제품 결정, 선택)

## 이미 정리된 계약 미확인 항목 (중복하지 않음)

- TIMS 쪽 미확인 항목은 `evaluation/design/tims_lowering_contract.md` 2절과 `geoflow/tims_contract.py`에 있다.
  - 주 시작일, 부분 구간, 빈 구간, null 반환, 상대 날짜 기준 시각, weekday·weekend·holiday 기간.
  - 날짜 범위 양 끝 포함, avg 분모, 날짜 귀속.
- 결정이 나오면 그 근거 위치를 위 `상태:` 줄에 `결정됨(근거 위치)`로 적는다.
- 결정에 기대는 라벨은 `label_basis`에 연결한다. 합성 셋의 기존 라벨을 바꿀 때는 이전 결과를 보존하고, 모든 비교 대상에 같이 적용한다.
